当我在思考和设计我的个人知识库应该是个什么模板的时候，在思考最开头的 yaml metedata 需要那些字段的时候，在最开始有这样子一个字段：category

这个字段意思非常的明确：文章分类。那个时候我直接参考的很多的博客的模板，比如说 hexo 还有很多其他的个人博客，当时他们又都这个字段，用于分类文章归属于哪一个种类，于是我自然的没有多想什么就加上了。

当时我的文章都是平铺的结构（articles 目录下面每一个目录都是一篇文章，所有文章之间都是同一个深度，articles\xxx

xxx.md），或许是因为当时文章只有几篇，并没有整理也没有成知识体系，这个时候靠着 category 这个 metadata 还是有用的，比如说 category: xxx/xxx/xxx

但是后来，随着文章不断增多，不仅仅是我的生活感悟，还有一些技术知识体系添加进来，我就发现这个平铺结构不够用了，于是开始将有关联的文章放在一起，整理他们。

随着不断的整理，我发现，文章的 category 标签和文章的路径基本上是一致的，后来我重新思考一边 category 标签存在的必要性，因为我有一个原则：越简洁越好（keep simple）

于是我决定取消这个 category 标签，完全采用文章路径来表达文章的分类。

后来我发现，这是相当有效的并且优秀的方法，在我的个人网站来解析的这个知识库的时候直接通过解析路径的方式拿到category, 并且非常容易找到对应的文章。

但是后来我也发现一个问题，一篇结合多了个方向文章分类困难，比如说一篇结合了 terraform, python flask, 的文章应该是放在 devops/ 下面还是 code/python 下面还是 cloud-infra/terraform 下面呢？

这个时候我一般会问问 codex 让他做一个判断，但是同时我也看到：Obsidian/Notion 那样的笔记文章之间存在双向链接的方式，我的想法是，我的笔记还不太多，大部分都是草稿，到时候再说吧。

后来我看到这一篇文章：[打败5000万美元向量数据库的Markdown文件 - 知乎](https://zhuanlan.zhihu.com/p/2020154671034037317)

其中提到了一个文件系统即上下文的概念，我深有感触，因为我的路径即为分类的这个概念似乎和这个有着不少的共鸣。
